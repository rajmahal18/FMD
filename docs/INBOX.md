# Participant offers

Organizer → Live operations → Participant inbox → New offer. Choose active participants grouped by team, write the offer, add attachments, review, then send. A batch supports up to 50 recipients and at most one participant from each assigned team. Choosing another person in a team replaces that team's selection; search retains all selections. The review lists names/teams and flags teams with no selection. Partial-team sends and unassigned participants remain supported. This is a selection rule for each send, not permanent Double Agent assignment or an event-wide offer limit.

Every selected participant receives a separate private message with their own final Yes/No answer. The participant has an envelope shortcut beside Account and a private event inbox. Selecting Yes or No requires an explicit final confirmation. No race, scoring, role or Double Agent mechanic changes happen on acceptance. Batch creation and attachment linking are atomic, and retries reuse the entire original batch.

Offers are saved before email is attempted. Each active event organizer receives a separate copy; an answer creates organizer response notifications. Use the existing `GMAIL_USER`, `GMAIL_APP_PASSWORD` and `APP_ORIGIN` configuration. No messages are sent by migrations, builds or tests. Email buttons open the authenticated inbox with a suggested answer; GET and email scanners never submit an answer. Sign-in/password change retains that destination.

Attachments support PDF, DOCX, PPTX, XLSX, UTF-8 text, PNG and JPEG: up to 5 files, 3 MB per file and 10 MB total per message. Each file uploads separately below typical hosting request limits, with a reusable upload key for retries. Names, sizes and file signatures are checked server-side. Files are stored privately as database bytes, shared across the batch instead of copied per participant. Only organizers and participants whose messages link to a file can download it. Downloads are attachments with private/no-store headers, nosniff and a sandbox policy; no public file URLs or attachment bytes appear in inbox JSON. Offers and organizer email copies carry the actual attachments. Response notifications link back to the offer without reattaching files.

Organizers can remove unused files from the draft. Sent attachments cannot be removed or edited. Unused uploads older than 24 hours are cleaned up on the uploader's next upload; sent files persist with their message history. Pause/archive blocks uploads and removal but preserves authorized downloads. Event deletion cascades files and links. Do not use upload success as proof the offer was sent; the final review/send is still required.

Email status is per recipient: pending, sending, accepted by the email server, failed, uncertain or skipped due to access changes. SMTP acceptance is not delivery/read confirmation. Explicit retry is available only for definite failures. Timeouts and abandoned sends remain uncertain to avoid automatic duplicate email. Replaying the same action retries pending envelopes without creating another offer or answer. A response is final; identical responses are idempotent and a conflicting response is rejected.

Every read/write checks active individual membership and role on the server. Participants see only their messages and no organizer email status or roster. Facilitators have no access. Responses must belong to the current participant. Paused/archived events are read-only. Inbox history remains across race resets because offers do not affect race state; event or membership deletion cascades messages/delivery records. Audits and management receipts record sending/responding/retry. Message content is escaped in HTML email.

Apply `20261104120000_participant_inbox` and `20261104140000_inbox_bulk_attachments` before deploying this feature. `npm run db:deploy` uses the configured database. Migrations never send offers or email.

Validation: `npm test`, `node tests/inbox-integration.mjs`, and `$env:INBOX_BROWSER_ONLY='1'; node tests/theme-smoke.mjs` after `npm run build`. Both inbox integration/browser tests use isolated databases and disable Gmail delivery. Pending inbox actions use actor/event-scoped tab storage and clear on sign-out.
